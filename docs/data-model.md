# Data model

The PostgreSQL schema (Supabase; Drizzle ORM), how JSON, decimal and time columns behave, and how
the schema is changed. Read this before touching `lib/db/`, adding a column or table, or writing a
query.

## Changing the schema

1. Edit `lib/db/schema.ts` (a new table ends `.enableRLS()`, like every other).
2. `pnpm db:generate` (drizzle-kit generate) → commit the new file under `lib/db/migrations/`.
3. `pnpm db:migrate` applies pending migrations locally; a production deployment applies them
   itself before it builds (`scripts/vercel-build.mjs` — [operations.md](operations.md#the-pieces)).
4. Add or extend the Zod schema in `lib/validations/`.

`pnpm db:push` is for local experiments only (interactive). A data change every database needs
(a row, a backfill) is a custom migration (`pnpm db:generate --custom --name=…`, SQL written by
hand, idempotent — `ON CONFLICT … DO NOTHING`, `WHERE NOT EXISTS`).

## Migrations on Postgres

- **A production deployment migrates before it builds, while the previous deployment still
  serves** — and keeps serving if the build then fails. So a migration must be safe for the code
  before it: add a column nullable or with a default, backfill, and drop or tighten only in a
  later deployment once nothing reads the old shape (expand, then contract).
- **The migrator runs all pending migrations in one transaction**, and Postgres DDL is
  transactional: a failed statement leaves the database as it was, schema included.
- **Write Postgres, not MySQL**: double-quoted identifiers, `ON CONFLICT` (never `INSERT IGNORE`
  or `ON DUPLICATE KEY`), no `FROM DUAL` or `@variables`, `CAST(… AS text)` (`AS CHAR` is one
  character). A literal in `INSERT … SELECT` is text: cast it to its column's type (`'x'::jsonb`,
  `'liter'::"product_unit"`); `INSERT … VALUES` casts by itself. `tests/unit/db/migrations.test.ts`
  refuses the MySQL forms and a file the journal does not name.
- **An enum change is `ALTER TYPE … ADD VALUE`** (drizzle-kit writes it); a value cannot be
  dropped in place — that is a new type and a column change.
- **Try a migration on a copy** before it reaches production: `createdb renovate_ge_try`, run
  `pnpm db:migrate` against it with `DATABASE_URL`, or against a Supabase branch on a paid plan.

### `projects`

One row per named project, holding both halves (the calculation and the 3D design). Column by
column, as the flow uses it, is [project-flow.md §6](project-flow.md); in short:

- identity and state: userId (every project since September 2026 has one; older guest rows
  have none), sessionId, `nameKa` (the person's name for it — set by
  `POST /api/projects/create`, changed only by `PATCH /api/projects/[id]`), status (`draft` =
  in progress / `saved` = confirmed with the save button or the checkout / `submitted` =
  ordered), createdAt, updatedAt;
- the calculation: `homeState` (NULL until chosen — migration 0011), totalM2, `rooms` (each
  with its walls one by one, `walls` — lengths — and `wallsM2` — net of doors and windows, JSON,
  no migration), `selectedProducts` (a pick may carry the product's `model3dKind` /
  `model3dUrl`: what it goes on on the board), `selectedFurniture`, **`calculatorEdits`**
  (`{ excluded, quantities, choices, progress }` — migration 0009), **`calculatorBoard`**
  (`{ plan, floorPlanUrl, finishes, electrical }` — 0011; `electrical`, the board's sockets,
  switches and lights, is JSON without a migration);
- the design: `mode`, `styleId`, `budgetGel`, `floorPlanUrl`, **`plan`** (rooms + walls,
  columns, beams, technical — a wall may be `built` (already standing in a black frame) or a
  room `separator` (thickness 0, not a wall); a room carries its `open` edges and `keepWhole`;
  a technical point its `product` (a radiator, a piece of equipment) and, equipment, the
  product's `sizeM`; all JSON, no migration — `lib/validations/design.schema.ts`), **`scene`**
  (items — a made-to-measure kitchen with its `kitchenMaterial`, the maker's product bought by
  the façade — finishes incl. per-wall and zones — a base floor two products share carries each
  one's `share` — electrical, **decor** (the code-built wall decor: family, wall, stretch,
  height, knobs and per-slot materials — [design-studio/decor.md](design-studio/decor.md)),
  **generation** (engine or AI, the model, the per-room notes, the AI run count), style profile,
  excluded, quantities, progress; a finish's product snapshot carries how it is sold, `sale`),
  **`versions`** (`DesignVersion[]` — 0006);
- concurrency: **`calculatorRev` / `designRev`** (each half's revision; a save from an older one
  is refused with 409 — 0012) and **`calculatorSaveId` / `designSaveId`** (the id of each
  half's last save — 0013);
- cost columns (`totalMaterialsCost`, `totalFurnitureCost`, `totalWorkersCost`, `totalCost`),
  stored **as edited** (ticks and quantities applied); a renovation's `totalCost` includes its
  15 % contingency ([budget.md](budget.md)).

The migration numbers above (0006, 0009, 0011 …) are where each column first
appeared, in the history before Postgres; on Postgres they are all in
`0000_baseline`.

Which half a project has is `projectKind` (`lib/projects/saved.ts`): a calculation is
`selectedProducts IS NOT NULL OR mode = 'full'`, a design is `plan IS NOT NULL`; a project can
be both.

## Rules for working with the data

- **Decimals are strings** (Drizzle `numeric`). Always `Number(...)` before arithmetic and
  `String(...)` before insert. An aggregate over one (`SUM(subtotal)`) is a string too; a count
  (`count(*)`, a `bigint`) is a number (`lib/db/index.ts` parses `int8`).
- **Whole numbers are whole.** An `integer` column refuses `1.6` (MySQL rounded it): round a
  measurement before it is written (`roundCm` in `scripts/seed-models.ts`).
- **JSON columns are `jsonb`** and come back parsed; their shapes are the types in
  `lib/design/types.ts` and `lib/calculator/types.ts` and the Zod schemas that validate them.
  `jsonb` keeps no key order or whitespace (MySQL's JSON did not either). In SQL: `col -> 'key'`,
  `col ->> 'key'` (text), `col @> '["modern"]'::jsonb` (contains), `jsonb_set`,
  `jsonb_path_query`.
- **Timestamps are `timestamptz`**, instants read as `Date`. The server runs on UTC; a day or a
  month taken in SQL says its zone (`to_char(created_at AT TIME ZONE 'UTC', 'YYYY-MM-DD')`, as
  the revenue report does). A raw `sql` that selects a timestamp gets the driver's text — map it
  (`.mapWith(projects.createdAt)`), as `MAX(…)` on the admin's accounts list does.
- **Text compares with case**, where MySQL's collation did not: e-mails are written and looked up
  in lower case (every route that takes one lower-cases it; the copy lower-cased the old rows), a
  search box uses `ilike` (drizzle) or `ILIKE` (raw SQL). A slug is lower case by construction.
- **Booleans are booleans** in raw SQL: `WHERE ${products.isActive}` / `NOT ${…}`, never `= 1`; a
  count of rows matching something is `count(*) FILTER (WHERE …)`, not `SUM(<condition>)`.
- **NULL sorts last going up in Postgres** and first in MySQL. Queries import `asc` / `desc` from
  `lib/db/order.ts`, which add `NULLS FIRST` / `NULLS LAST` to a nullable column (or an aggregate)
  so lists keep the order they had ("last sign-in, newest first" lists those who never signed in
  last); a NOT NULL column sorts as drizzle's own, so an index still serves it.
- **An insert's id, an update's rows**: `.returning({ id: table.id })` — there is no `insertId`
  or `affectedRows`. A conditional write that must know whether it won (a revision check, a
  credit claimed once, an order confirmed once, an upload claimed once) reads the length of its
  `.returning()`.
- **No statement is prepared by name** (the transaction pooler hands each statement any
  connection): use drizzle's queries as they are, not `.prepare('name')`.
- **Public product queries** must require `products.isActive`, `storeId IS NULL OR
  stores.isActive` (a pending store is inactive) and `ownerUserId IS NULL` (people's own
  furniture). `publicProductCondition` in `lib/api/productAccess.ts` is the reference, with the
  per-row checks beside it; the catalogue page, the landing wall and the design catalogue still
  write the same conditions inline ([catalog.md](catalog.md#who-sees-a-product-libapiproductaccessts)).
- **Server code never trusts a client's prices**: saves and checkouts reprice from the catalogue
  ([project-flow.md §10](project-flow.md), [marketplace.md](marketplace.md)).

## Drizzle: correlated subqueries in `.select({})` don't correlate

A `sql` template with a correlated `select count(*) ... where products.store_id = stores.id`
used as a *field* inside `.select({})` silently returned 0 for every row — it was emitted
uncorrelated. Use `leftJoin` + `groupBy` + `count()` instead (`app/admin/stores/page.tsx` does,
with a comment). A correlated `NOT EXISTS (…)` inside `.where()` is in use on the admin
dashboard (`app/admin/page.tsx`); check the result of any new correlated subquery by hand.

## Don't sort rows that carry big JSON

When no index gives an `ORDER BY` its order, the database sorts the rows with every column the
select reads — a JSON column whole, even when the select only takes `col -> 'x'` or
`col IS NOT NULL` of it. A project's `scene`, `versions` and `calculator_board` reach hundreds of
kilobytes once a design is furnished. MySQL failed such a sort outright (its 256 KB sort buffer —
"Out of sort memory", which broke the hubs once); Postgres spills it to disk instead, which is
only slow. So a query that orders `projects` still sorts in code, selects only small columns, or
orders by an index — the profile's `userId` + `createdAt` has one (`projects_user_created_idx`).
The hubs' query (`loadHubProjects`) sorts in code; the admin's projects list and the dashboard's
newest projects sort and cut the page on the ids alone, then read those rows by id, back in order
through `inIdOrder` (`lib/admin/list.ts`).

## Tests

The schema itself has no tests; `tests/integration/save-routes.test.ts` mocks `@/lib/db` to test
the project routes' writes (revisions, column ownership, repricing), and
`tests/unit/db/migrations.test.ts` keeps every migration Postgres and in the journal
